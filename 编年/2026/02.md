# 2026年2月

## Codex App：多 Agent 的“指挥中心”进入桌面

> 1 月 GitHub 刚把 Agent session 做成 repository 里的管理对象；**2 月 2 日，OpenAI 发布 Codex App，直接把产品定义为“a command center for agents”。** 并行 Agent、isolated worktree、background task、skills 与 automations 被放进同一个桌面工作台。三天后 GPT-5.3-Codex 又把 Codex 从“写代码的 Agent”推进到“在电脑上完成几乎所有开发者和专业人士工作”的方向。Agent 的组织形态开始从单个会话转成一组可管理的工作进程。

### Codex App：Command Center for Agents

**2026-02-02** — OpenAI 发布 **Codex App for macOS**。[^1]

OpenAI 官方直接把它称为：

> **A command center for agents.**

核心能力包括：

- **多个 Agent 并行工作**；
- 使用 isolated worktrees 减少同时修改代码的冲突；
- 运行 long-horizon / background tasks；
- 观察进度与 clean diff；
- 使用 reusable **skills**；
- 用 **Automations** 委派重复工作。

这不是普通 IDE 的 UI 改版。

它意味着 Agent 产品的管理对象已经从“一次聊天”切换成：

> **多个独立、并发、有生命周期的任务执行单元。**

用户角色也随之变化：不是和一个 Agent 持续对话，而是像管理 build jobs、workers 或团队任务一样，分配、查看、接管和验收多个 Agent。

### Worktree：多 Agent 协作必须先解决写冲突

多 Agent 最直观的问题不是“它们会不会合作”，而是**同时写同一份世界状态怎么办**。

在软件工程里，这个问题非常具体：两个 Agent 如果都直接修改当前 working tree，很容易互相覆盖文件、破坏未提交改动。

Codex App 因而把 isolated worktree 变成核心交互结构。

这揭示 multi-agent 工程的一个一般规律：

> **并行推理之前，必须先定义并行写入的隔离边界。**

在代码里是 worktree；在数据库里可能是 transaction / branch；在文档系统里可能是版本、锁或 merge；在物理 Agent 中则会变成设备资源仲裁。

### Skills 与 Automations：Agent 能力从对话记忆变成可复用资产

Codex App 还把 **skills** 和 **automations** 放进产品核心。[^1]

这延续了 Voyager 的 skill library、2025 年 Agent runtime 与事件驱动执行的长线：

- 会话历史记录“以前说过什么”；
- skill 记录“这类工作怎样做”；
- automation 记录“什么时候自动做”。

三者分别对应：

> memory → procedure → trigger

一个长期 Agent 系统不可能每次都从 prompt 重新发明工作方法。技能和自动化因此是**组织记忆**的一部分。

### GPT-5.3-Codex：从 Coding Agent 到 Computer Work Agent

**2026-02-05** — OpenAI 发布 **GPT-5.3-Codex**。[^2]

官方称其将 GPT-5.2-Codex 的 coding 能力与 GPT-5.2 的 reasoning / professional knowledge 合并，并提升约 25% 速度。

更值得 Agent 史记录的是官方定位变化：

- 能处理 research；
- tool use；
- complex execution；
- long-running tasks；
- 用户可以在它工作期间继续 steer / interact，而不丢失上下文。

OpenAI 甚至直接写道：Codex 从“write and review code”推进到**几乎覆盖开发者与专业人士在电脑上完成的全部工作**。[^2]

这说明 coding agent 的边界正在向 general computer-work agent 外溢。

软件工程之所以先跑通，不代表 Agent 最终只属于软件工程；它更像是最先建立出可靠 verifier、sandbox 与 state management 的试验场。

### “参与创造自身”：Agent 开始进入 AI 开发流水线本身

OpenAI 还称 GPT-5.3-Codex 是首个在自身创建过程中发挥关键作用的模型：团队使用早期版本调试训练流程、管理部署、诊断测试与评估。[^2]

这类说法要谨慎理解。

它不等于模型“自主训练了自己”，也不应写成递归自我改进已经实现。

更准确的是：

> **Agent 已经进入模型研发组织的工程工具链。**

AI 开发 AI 不再只是代码补全，而开始覆盖训练运维、部署和评估流程。

### 安全能力也跟着行动半径升级

GPT-5.3-Codex 的 system card 将其作为 OpenAI 首次在 Preparedness Framework 下**按 cybersecurity High capability 部署**的发布，并启用相应 layered safeguards。[^3]

OpenAI 同时强调：目前并没有确定证据表明模型已经跨过 High threshold，而是因为无法排除可能性而采取预防性处理。

这很符合 Agent 安全史的发展：

模型越能长期使用工具和计算机，能力风险越不能只由最终文本衡量。

要同时看：

- 运行时权限；
- 网络访问；
- sandbox；
- 执行持续时间；
- 自动化规模。

### 同月模型继续密集迭代

2 月仍有多个重要模型更新，包括 Claude Sonnet 4.6 等。Anthropic 将 Sonnet 4.6 的改进明确覆盖 coding、computer use、long-context reasoning 与 **agent planning**，并把 1M context 推入 Sonnet 层。[^4]

这里不逐一做模型排行榜。它们共同说明：到 2026 年初，**Agent planning / computer use 已经从特殊旗舰能力进入主流产品层。**

### Anthropic 的蒸馏攻击指控

**2026-02-23** — Anthropic 公开指控 DeepSeek、Moonshot AI、MiniMax 通过大规模账户与交互收集 Claude 输出，用于模型蒸馏。[^5]

该事件详细事实与各方证据边界见《知识蒸馏与模型压缩》及 3 月编年。

放在 Agent 史里，这件事还有一个侧面：当 Agent 能高速自动调用外部模型 / API，传统“用户一次问一个问题”的服务条款假设开始失效。

**自动化调用本身就是能力放大器。**

于是 rate limit、identity、abuse detection、credential policy 也成为 Agent 基础设施的一部分。

### 评曰

Codex App 的历史意义，不是“终于有一个漂亮的 Codex GUI”。

它真正把一个新的软件对象摆在普通用户面前：

> **Agent task。**

它有自己的工作区、进度、产物、持续时间，可以并行，也可以被自动触发。

这比聊天会话更像一个进程；比传统程序更像一个带推理能力的 worker。

从这里开始，Agent 产品会越来越像任务操作系统：

> schedule、isolate、observe、resume、merge、approve。

模型只是运行这些工作单元的大脑。
