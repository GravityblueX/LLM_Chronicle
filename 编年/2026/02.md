# 2026年2月

## Agent 任务成为“进程”，权限风险也随之暴露：Codex App、OpenClaw 安全警告与 GPT-5.3-Codex

> 1 月 OpenClaw 把“自己的机器、自己的 Agent”推成极具传播力的个人产品形态；2 月紧接着发生的事情提醒行业：**拥有自己的 Agent，也意味着把文件、shell、消息渠道和 credentials 交给一个概率系统。** 同月 OpenAI 的 Codex App 又把多个 Agent 做成可并行管理的桌面任务。Agent 一边越来越像进程管理，一边开始暴露真正的进程级权限风险。

### Codex App：Command Center for Agents

**2026-02-02** — OpenAI 发布 **Codex App for macOS**。[^1]

OpenAI 官方直接把它称为 **“A command center for agents.”** 核心包括多个 Agent 并行工作、isolated worktrees、long-horizon / background tasks、Skills 与 Automations。

这意味着 Agent 产品的管理对象从“一次聊天”切换成：

> **多个独立、并发、有生命周期的任务执行单元。**

Worktree 的加入尤其说明 Multi-Agent 最先遇到的往往不是“会不会合作”，而是**同时写同一份世界状态怎么办**。在代码里是 worktree，在数据库里可能是 transaction，在文档里可能是版本 / lock，在物理 Agent 中则是设备资源仲裁。

### 2 月 4—5 日：OpenClaw 爆红的另一面——一只龙虾拿到了过多权限

**2026-02-04** — Bloomberg 报道 OpenClaw 在快速爆红的同时出现高权限个人 Agent 的现实安全问题。报道记录过一个具体案例：用户给 Agent iMessage 等能力后，系统出现失控行为，向本人、家人和随机联系人连续发送数百条消息。[^6]

这个案例不能用来证明“OpenClaw 普遍会失控”；它只是一个个案。但它非常适合说明 Agent 产品与聊天模型的差异：

> **失败不一定表现为“回答错了”，还可能表现为“做多了、做错对象了、做了无法轻易撤回的事”。**

**2026-02-05** — Reuters 报道中国工信部门对 OpenClaw 相关公开暴露、身份认证和访问控制风险发出警告；报道同时指出阿里云、腾讯云、百度等已开始提供与 OpenClaw 有关的部署 / 托管能力。[^7]

因此，中国后来 3 月的“养龙虾”热潮并不是在风险尚未知晓时发生。更准确的时间顺序是：

> **OpenClaw 爆红 → 安全案例与监管警告出现 → 地方和厂商仍继续大规模推广与产品化。**

这解释了随后中国市场看似矛盾的两幅图：地方政府举办安装活动、发补贴；银行、政府机构和安全部门又限制在办公设备上安装。

### OpenClaw 的安全问题为什么比普通聊天更难

OpenClaw 的典型链条同时包含：

- messaging channel；
- model；
- workspace；
- shell / browser；
- credentials；
- Skills；
- persistent gateway。

其中任何一层都可能成为攻击面。

“本地运行”可以减少部分数据被第三方云托管的依赖，却**不等于自动安全**。恶意 Skill、prompt injection、错误 shell command、暴露 gateway、过宽 credential permission 仍可能在本地造成更直接的后果。

这也是以后“腾讯 / 百度 / 阿里版龙虾更安全”一类宣传需要谨慎处理的原因：史书首先能确认的是厂商增加了 sandbox、权限、审计或托管设计；至于这些设计是否真的降低事故率，需要独立安全研究与生产数据。

### GPT-5.3-Codex：从 Coding Agent 到 Computer Work Agent

**2026-02-05** — OpenAI 发布 **GPT-5.3-Codex**。[^2]

官方称其合并 GPT-5.2-Codex 的 coding 能力与 GPT-5.2 的 reasoning / professional knowledge，并提升速度；产品定位扩展到 research、tool use、complex execution 与 long-running tasks。

OpenAI 还称 GPT-5.3-Codex 在自身研发流程中发挥了关键作用，用于调试训练流程、管理部署、诊断测试与评估。这里不应写成“模型自主训练了自己”；更准确的历史事实是：

> **Agent 已经进入 AI 模型研发组织自己的工程流水线。**

### 安全能力也跟着行动半径升级

GPT-5.3-Codex system card 将其作为 OpenAI 首次在 Preparedness Framework 下**按 cybersecurity High capability 部署**的发布，并启用相应 layered safeguards。[^3]

这再次说明 Agent 安全不能只看模型最后说了什么，还要看：

- runtime permission；
- network access；
- sandbox；
- task duration；
- automation scale。

### 同月模型继续 Agent 化

Anthropic 的 Sonnet 4.6 改进也明确覆盖 coding、computer use、long-context reasoning 与 **agent planning**。[^4]

这些是厂商能力声明与产品定位；不能据此直接推出“开放世界任务已稳定无人化”。真正成熟度仍应由重复任务成功率、人工接管、成本和真实生产数据来衡量。

### Anthropic 的蒸馏攻击指控

**2026-02-23** — Anthropic 公开指控 DeepSeek、Moonshot AI、MiniMax 通过大规模账户与交互收集 Claude 输出用于模型蒸馏。[^5]

该事件详细事实与各方证据边界见《知识蒸馏与模型压缩》及 3 月编年。

放在 Agent 史里，它还有另一面：当自动化系统可以高速调用外部模型 / API，传统“一名用户一次问一个问题”的服务条款假设开始失效。rate limit、identity、abuse detection 与 credential policy 于是也成为 Agent 基础设施。

### 评曰

2026 年 2 月让“Agent task”这个新软件对象的两面同时变得清楚。

Codex App 让它像一个可并行管理、可隔离、可恢复的任务进程；OpenClaw 的安全案例则说明，一旦这种进程获得个人文件、消息、shell 和 credentials，它的错误也会从信息错误变成状态错误。

因此 Agent 产品成熟度不能只问：

> **它能做多少种事？**

还要问：

> **同一件事能稳定做多少次？做错后能不能停、撤回和恢复？**

这个问题会成为 3 月中国“养龙虾”全民热潮最容易被宣传掩盖的部分。
