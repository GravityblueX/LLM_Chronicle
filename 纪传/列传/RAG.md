# 《RAG 列传》

> RAG（Retrieval-Augmented Generation，检索增强生成）不是某一个模型，而是一种把"先查后写"刻进语言模型工作流的方法。它的核心逻辑很朴素：语言模型不一定什么都记住，但如果能在生成前翻一下资料库，回答就会更准、更可溯源。从 2020 年首次系统提出，到 2024 年后成为大模型产品的基础设施，RAG 走了一条"从稀缺到标配"的整合之路。

---

## 一、技术背景

语言模型有一种天然的困境：知识都在参数里，但参数不会自动更新。

GPT-3 发布后，大家惊讶于它的 few-shot 能力，也发现了它的脆弱：它会自信地编造不存在的事实，不知道训练截止日期之后发生的事，也无法告诉用户答案具体来自哪里。微调可以补充一些知识，但成本高、慢，而且旧知识与新知识混在一起很难分开管理。

在 RAG 被明确提出之前，已经有几件事在铺垫：

- **Open-book QA**：让模型在回答问题前先看一个或多个相关文档，而不是只靠记忆回答（如 DrQA, 2017）
- **Dense retrieval**：用神经网络把查询和文段嵌入同一空间，内积或余弦相似度就是相关性分数，代替传统的 TF-IDF 或 BM25（如 DPR, 2020）
- **REALM**：把检索器和语言模型一起训练，检索到的文档被编码后喂给语言模型做预训练和微调（Guu et al., 2020）

这些工作证明了一件事：检索和生成不应该是两个独立的阶段，而是可以联合优化、相互增强的。

## 二、核心创新

### 2.1 原始 RAG：把检索变成可微分的生成前端

2020 年，Lewis 等人（Facebook AI Research）发表《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》，正式提出 RAG 并用这个缩写给方法命名。[^1]

RAG 的架构很直接：一个查询进来，先过一个检索器（用 DPR 的 dense retriever），从维基百科中找到 top-k 相关文档片段；再把这些片段拼到输入里，送给一个 seq2seq 模型（BART）生成回答。

论文设计了两个版本：

- **RAG-Sequence**：检索到的文档被当作隐变量，每个文档各自生成一段回答，最后用检索概率和生成概率的乘积选出最优
- **RAG-Token**：生成每个 token 时都可以从不同文档中抽取信息，文档贡献在 token 级别动态决定

和 REALM 的不同在于，REALM 是在预训练阶段做检索增强，而 RAG 把检索作为一个通用的生成前端——适用于微调和推理阶段，不要求从零训练。

论文在多个知识密集任务（开放域问答、事实验证、Jeopardy 问题生成）上展示了 RAG 的优势：不但在标准基准上达到当时最好的成绩，而且生成的内容因为直接引用检索文档，更可溯源、幻觉更少。

RAG 的历史作用，是把"参数知识"和"外部知识"的边界正式划开了。语言模型的参数负责语言能力和通识推理，检索系统负责事实存储和新鲜度。二者分工明确，各行其是。

### 2.2 DPR 与密集检索：让"找到对的文档"变成一门技术

RAG 的检索器选的是 DPR（Dense Passage Retrieval）。DPR 本身也是一篇很重要的论文。[^2]

Karpukhin 等人在 2020 年提出 DPR：用一个 BERT 编码查询，另一个 BERT 编码文档，两者的点积就是相关性。训练目标是负对数似然：正样本是给定的正确文档，负样本随机采样自其他文档。相比 BM25 等传统方法，DPR 对语义更敏感——"首都"和"首府"在词面上不匹配，但在 dense 向量空间里接近。

DPR 论文展示了几个重要特性：

- "随机负样本"已经很好，"困难负样本"（检索靠前但与问题无关的文档）更好
- 用 FAISS 做近似最近邻检索，速度足够支持实时推理
- 在 Natural Questions、TriviaQA 等开放域 QA 基准上大幅超过 BM25

DPR + RAG 的组合，形成了 2020—2022 年检索增强的基本范式：密集向量检索 → top-k 文档 → 拼入上下文 → 生成回答。

### 2.3 2023—2024：RAG 从论文走向工程栈

ChatGPT 在 2022 年底发布后，RAG 的需求突然从学术任务变成了产品需求。企业想用自己的内部文档、客服知识库、产品手册来增强模型回答，但不想微调模型。RAG 正好契合：把文档切块、转成向量、存进向量数据库，用户提问时检索最相关的几段，喂给模型生成。

这一阶段的关键产品化变化：

- **LangChain + LlamaIndex 的编排框架**：把文档加载、分块、嵌入、向量存储、检索、生成串成 pipeline
- **向量数据库爆发**：Pinecone、Weaviate、Milvus、Qdrant 等专用向量数据库获得大量融资和采用
- **RAG 评估标准出现**：RAGAS、TruLens 等框架提供忠实度、相关性、召回率等评估指标

但这轮工程化也暴露了原始 RAG 的几个瓶颈：

- 分块太粗则检索不准，太细则上下文不完整
- 检索多少文档合适？太少可能漏掉关键信息，太多可能塞满上下文窗口
- 用户提问往往不是好的检索查询——用口语问"你们那个蓝色的、上个月降价的产品叫啥"很难搜到

### 2.4 高级 RAG：自我纠错、图检索、多轮推理

2023—2024 年，RAG 的研究方向转向"让检索更聪明"：

**Self-RAG**（Asai et al., 2023）：让模型自己决定什么时候需要检索、什么时候不用；检索后自己评估文档是否相关、是否支持回答——如果不行就再检索。[^3]

**Corrective RAG（CRAG）**：检索后先评估文档质量，如果不够好就用网络搜索补充，再重新生成。相当于给 RAG 加了自检和纠错机制。

**GraphRAG**：不把文档当孤立的片段，而是先建知识图谱——节点是实体，边是关系——检索时在图谱上做多跳查询。微软 2024 年把 GraphRAG 开源，强调它比传统 RAG 更能处理多实体、多跳的复杂问题。[^4]

**多轮 RAG**：不是一次检索就生成答案，而是检索→生成→根据生成结果再检索→再生成。类似 ReAct 或 Toolformer 的思路，但专精于知识检索。

这些高级 RAG 的共同方向是：把检索从"生成前一道简单的预处理"变成"生成过程中多次、多策略、可纠错的主动行为"。

### 2.5 RAG vs 长上下文：竞争还是互补

2023—2024 年，大模型上下文窗口迅速拉长：GPT-4 Turbo 128K、Claude 200K、Gemini 1M、Llama 3.1 128K。随着上下文变长，一种声音出现了：能不能直接把所有文档塞进上下文，省掉检索？

实践给出的答案比口号复杂：

- 把几百页文档全放进上下文，推理成本、显存、延迟都会涨，且模型在堆积信息中"迷失"（lost-in-the-middle 效应）[^5]
- RAG 的检索是一种有选择的取舍——只喂最相关的几段——在成本和效果之间做平衡
- 长上下文更适合需要完整上下文才能处理的任务（如整本书总结、长代码审查）；RAG 更适合从海量文档中找到特定信息
- 两者不是二选一，而是组合：用 RAG 筛选出相关段落，再用长上下文容纳整个筛选结果

2024 年以后的主流产品做法，基本是 RAG + 长上下文混用。模型可以处理更长的输入，但检索仍然负责从海量文档中挑出真正重要的部分。

### 2.6 关键数据

| 时间 | 工作 | 核心贡献 | 历史作用 |
|------|------|----------|----------|
| 2020-04 | DPR | 双编码器密集检索，超越 BM25 | 为 RAG 提供高性能检索器 |
| 2020-05 | REALM | 预训练阶段做检索增强 | 打破"检索只在推理时用"的边界 |
| 2020-12 | RAG (Lewis et al.) | 检索 + seq2seq 生成，联合概率建模 | 正式提出 RAG 范式，命名并定义 |
| 2023 | Self-RAG | 模型自己判断何时检索、是否相关 | 把检索从外部固定规则内化为模型决策 |
| 2024 | GraphRAG | 知识图谱 + 多跳检索 + LLM 生成 | 解决传统 RAG 的多实体复杂查询盲区 |
| 2024 | 长上下文+RAG 融合 | 用检索筛选，长上下文容纳 | 形成 2024 年后 RAG 工程主流模式 |

## 三、影响与后继

### 3.1 企业 AI 落地的默认配方

到 2026 年，RAG 已经成为企业 AI 应用的标准组件。客服机器人、内部知识库问答、法律合同审查、医疗文献检索、代码库问答——几乎任何需要"模型 + 专有知识"的场景，第一版方案都是 RAG。

这不是因为 RAG 是技术上最优雅的方案，而是因为它的工程门槛最低：不需要微调模型，不需要标注训练数据，只需要把文档整理好、向量化、建好检索。企业可以先跑起来，有反馈后再决定哪些环节需要微调或强化。

### 3.2 Agent 时代 RAG 的新角色

Agent 模型把 RAG 推到了更主动的位置。在 ReAct、AutoGPT、Claude Code 等工作流里，模型不只是"被喂检索结果"，而是"自己决定去查什么"。

这就产生了多步检索、工具调用和记忆整合的问题。模型看到一个问题 → 决定需要查什么 → 从向量库、网络搜索、代码仓库、数据库中分别取回信息 → 再综合生成。每一步检索都是一次 RAG，但整个流程已经远超原始 RAG 的单次检索范式。

### 3.3 未被解决的张力

RAG 也有长期存留的张力：

- **分块策略没有通用最优解**：不同的文档类型（法律、代码、百科、对话日志）需要不同的切分方式，过度分和不足分都伤效果
- **嵌入模型的可迁移性**：通用嵌入（如 text-embedding-3）在企业专有文档上不一定最优，但微调嵌入又需要标注数据
- **跨语言和跨语种的检索质量**：混合中英文档、多语言知识库、口语化查询的检索是弱区
- **RAG 的安全和权限**：检索出来的文档可能包含敏感信息，如何在检索和生成之间做访问控制，还没有统一方案

### 3.4 消退或被吸收

RAG 不太可能"消失"，但它正在从"一个独立的技术方向"变成"大模型系统设计中的基础模块"。就像 2010 年代的检索不再是独立研究方向而是搜索系统的默认组件一样，RAG 正在嵌入框架、平台和产品标配。

它的精髓——把知识放在参数外面，需要时去取——已经不会回退。任何人说"大模型接上自己的数据"，最自然的实现就是某种形式的 RAG。

## 评曰

RAG 的贡献，不是发明检索，而是把检索变成语言模型生成的一个标准步骤。

在它之前，人们已经知道"先查资料再回答"比"空想"更靠谱——搜索引擎做了二十多年。但 RAG 把这一步变成了可微分、可联合优化、可工程化的模块：密集检索器与生成器用概率语言讲通，中间文档作为可追溯的证据链路保留。

RAG 的发展像一条不断拓宽的河床。早期它只是机器阅读理解的一个后缀；ChatGPT 之后，它成了所有"模型 + 私域数据"方案的第一选择；Self-RAG 和 GraphRAG 又给它加了纠错和多跳推理。长上下文窗口的出现没有杀死它，反而让它从"不得不检索"变成了"有选择地检索"——更精准、更经济、更可控。

历史会记住 RAG，不是因为它提出了什么惊世的算法，而是因为它找到了模型能力与人类知识库之间最短、最实际的那座桥~
