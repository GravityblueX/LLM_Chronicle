# 开源与闭源：从模型许可证到智能控制权

> 大模型时代的“开源 / 闭源”曾被讲成一场价值观战争：一边代表公共基础设施，一边代表商业垄断。到 2026 年，这种二分已经解释不了现实。Kimi K3 和 Qwen3.8 的权重可以公开，却常常需要大型云集群才能真正运行；Muse Glimmer 能在个人机器长期驻留，反而提供另一种更直接的自主权；Claude 完全闭源，却通过 Fable / Mythos 把能力和风险访问分层；DeepSeek-V3 甚至同时存在 MIT 代码和带限制的模型许可证。真正需要讨论的，不再只是“权重放不放”，而是：**谁能检查、修改、运行、托管、分发、治理和最终关闭这套智能。**

---

## 一、闭源最强的东西不是保密，而是可撤回性

GPT-3 以后，OpenAI 把前沿模型主要做成 API 服务。Claude、Gemini 也延续了托管路线。

通常人们强调闭源的商业优势：

- 模型权重不能被竞争者直接复制；
- API 可以持续收费；
- 产品和模型版本统一；
- 训练数据与工程方法保密。

但 Agent 时代更值得注意的是另一点：**托管能力可以被动态治理。**

厂商可以：

- 修复系统提示；
- 更新 abuse classifier；
- 限制某类工具；
- 下线某版本；
- 针对高风险用户增加验证；
- 调整地域和组织访问。

Anthropic 在 2026 年的 Fable / Mythos 体系把这一逻辑推得最明显：相同底层模型因为 safeguards 和 trusted access 不同，可以成为不同产品层。[^1]

这说明闭源 / 托管最重要的安全属性可能不是“秘密”，而是**部署后的控制面仍在。**

权重没有离开服务器，就还可以改变未来的访问规则。

---

## 二、开放权重最强的东西不是免费，而是不可撤回性

开放权重的基本事实相反。

一旦模型参数进入公共网络：

- 原厂不能强制升级；
- 不能统一改变 system prompt；
- 不能撤回已经下载的副本；
- 下游可以量化、微调、蒸馏、去掉某些 safeguards；
- 可以部署在原厂完全看不到的网络里。

这就是开放权重最强的自由，也是最强的风险属性。

LLaMA 1 的泄漏已经演示过这种不可逆性；DeepSeek-R1、Qwen、Kimi 等则把它变成主动发布策略。

因此开放权重不是“API 的免费版本”。它改变的是**控制权的归属**。

---

## 三、旧的“开源三层皮”还不够：2026 至少有六个维度

过去常把开放拆成：权重、代码、数据。

现在还必须加上运行和分发：

| 维度 | 核心问题 |
|---|---|
| 权重 | 我能拿到参数吗？ |
| 许可 | 我能合法修改、商用、再分发吗？ |
| 训练透明度 | 我知道它从哪里来、怎样训练吗？ |
| 可运行性 | 我的硬件真能运行它吗？ |
| 托管 / 分发 | 实际企业使用是否仍依赖某家云？ |
| 治理控制 | 谁有能力升级 safeguards、撤销访问、审计调用？ |

同一个模型在六轴上可以处于完全不同的位置。

这使“开源程度排行榜”变得意义有限。

---

## 四、许可证没有单向走向更宽松

旧叙事容易把历史写成：研究许可 → Llama 商用许可 → Apache → MIT，仿佛模型越强，许可证必然越自由。

事实不是这样。

### 4.1 DeepSeek-V3：代码和模型许可可以分裂

DeepSeek-V3 的代码使用 MIT，但模型权重受 DeepSeek Model License 约束，并包含 use-based restrictions。[^2][^3]

R1 才明确把主模型权重与代码都放到 MIT，并允许修改、衍生、商业化和蒸馏。[^4]

所以“DeepSeek 从 V3 起全面 MIT”是错误的简化。

### 4.2 Qwen：不同尺寸与代际许可并不完全相同

Qwen2.5 的多个尺寸使用 Apache 2.0，但并非所有尺寸完全一致；Qwen3 进一步扩大 Apache 路线；Qwen3.8 又把 Max 级旗舰推进开放权重。[^5][^6]

开放边界在扩大，但不是一条没有例外的直线。

### 4.3 Kimi K3：非常宽，但仍是自定义许可证

Kimi K3 License 允许使用、修改、分发、部署和创建衍生物等广泛权利，但它仍是 Moonshot 自定义模型许可证。[^7]

历史记录最重要的是写清**具体条款名称**，而不是为了叙事方便统一塞进“MIT 开源”。

---

## 五、OSI 解决的是语言纪律，不是产业胜负

Open Source Initiative 在 2024 年发布 OSAID 1.0，希望把 AI 系统的使用、研究、修改和分享自由，以及数据、代码、参数等“首选修改形式”纳入定义。[^8]

它最现实的贡献不是裁决“谁才配叫开源冠军”，而是迫使行业承认：

> **开放权重只是开放的一部分。**

本项目因此优先使用：

- open-weight / 开放权重；
- Apache 2.0 权重；
- MIT 模型；
- 自定义开放许可；
- 托管闭源模型。

尽量不用含糊的“完全开源”，除非数据、代码、权重和使用自由都有足够证据。

---

## 六、Kimi K3 / Qwen3.8：开放权重撞上算力所有权

2026 年最能改变开源讨论的，不是又一个许可证，而是模型变得太大。

**Kimi K3**：2.8T 总参数、104B 激活、百万上下文。[^9]

**Qwen3.8-2.4T-A95B**：2.4T 总参数、约 95B 激活、百万上下文。[^10]

两者都把前沿旗舰推向开放权重，但也把一个问题放到台面上：

> **如果权重人人可以下载，但只有少数机构有机器高效运行，它究竟开放了什么？**

答案仍然很多：

- 可以研究架构；
- 可以审计权重；
- 可以二次训练；
- 可以让第三方云托管；
- 可以避免单一 API 厂商锁定。

但“个人完全控制前沿模型”这件事并没有因此实现。

稀缺性从权重转移到了 GPU、互联、内存、专家并行和推理软件。

开放权重改变了**知识产权控制**，却没有自动消除**资本密集型基础设施控制**。

---

## 七、Muse Glimmer：小模型让“运行权”重新成为开放指标

Meta 在 **2026-08-10** 发布 30B Muse Glimmer，以 Apache 2.0 开放权重，并明确面向 Mac / PC / 单张消费级 GPU 的 always-on local agent。[^11]

这给“开放”增加了另一条轴：

> **我能不能在自己的机器上持续运行它，而不是把私人上下文送进云？**

在这个意义上，一个 30B 模型可能比 2.8T 模型提供更强的用户主权：

- 数据留在本地；
- 断网可工作；
- runtime、memory 和工具完全由用户控制；
- 厂商不能远程改变模型行为。

所以开放模型未来很可能分成两条路线：

1. **开放前沿**：尽可能把最强权重公开；
2. **开放运行时**：尽可能让真实设备拥有足够强的本地智能。

二者不是一回事。

---

## 八、云并不是开放权重的敌人，反而可能是它的分发层

Kimi K3 权重开放之后，Reuters 在 2026-08-26 报道 Moonshot 正与 Microsoft、Amazon、Google 洽谈云托管与收入分成。[^12]

这个组合看似矛盾：

> “模型都开放了，为什么还需要商业云？”

原因很简单：**权重复制成本接近零，前沿推理成本不是零。**

大型云可以卖：

- GPU 容量；
- 高速互联；
- 自动伸缩；
- inference engine；
- 企业安全；
- SLA；
- 数据地域；
- 计费和审计。

这和 Linux / PostgreSQL / Kubernetes 非常相似：开源软件没有消灭 Red Hat、AWS、云数据库和托管 Kubernetes。

开放权重可能最终让“卖模型文件”失去意义，却让“把模型可靠跑起来”变成更大的服务市场。

---

## 九、闭源也在越来越“开放接口化”

反过来，闭源模型也不是一堵完全封闭的墙。

MCP、A2A、function calling、Responses API 等协议使开发者可以在不拥有权重的情况下，把模型嵌入相对可迁移的 Agent 系统。

如果工具协议、state store 和 artifact 层独立于模型，那么企业可能做到：

- 今天用 Claude；
- 明天换 GPT；
- 某些任务用 Gemini Flash；
- 敏感任务用本地 open-weight；
- 状态和数据不随着模型一起迁移。

这是一种**接口层的开放性**。

所以供应商锁定也不再只是“有没有权重”决定，而取决于：工作流、数据、memory、工具和权限是否能跨模型迁移。

---

## 十、安全争论正在从许可证变成能力阈值

Anthropic 长期担心高能力模型开放后的不可逆风险，但 Dario Amodei 在 **2026-07-27** 明确表示：Anthropic 从未倡议禁止 open-weight models；不具有危险能力的开放权重模型可以是公共品。[^13]

真正争论的是：

> 当模型达到怎样的 cyber / bio / autonomous 能力时，不可撤回权重扩散的风险超过公共收益？

这不是许可证能单独解决的问题。

同一个 MIT 文件不会告诉你：模型能不能设计复杂生物流程，能不能自动发现网络漏洞，能不能长期自主操作。

所以未来的开放治理很可能同时需要：

- 能力评估；
- 权重发布政策；
- 模型许可证；
- 云访问控制；
- 硬件 / 出口规则；
- runtime safeguards。

“开放与安全”从价值观辩论变成多层治理系统。

---

## 十一、真正的两种社会契约

如果仍然要保留“社会契约”这个比喻，那么 2026 年的两种契约应该重新写。

### 托管模型契约

> 你把权重、运行和更新权交给供应商；供应商承诺给你稳定服务、安全更新、低运维成本和责任边界。

用户得到便利，但接受黑箱、版本变化和访问可能被改变。

### 开放权重契约

> 供应商放弃对已分发权重的持续控制；用户获得复制、部署和修改的更大自主权，同时承担硬件、运维、安全和合规责任。

用户得到控制权，但也接过了责任。

所以这不是“自由 vs 垄断”，而是**控制权与责任怎样分配**。

---

## 十二、混合架构可能比纯路线更常见

一个真实企业完全可以同时拥有：

- 本地小模型处理敏感资料；
- Qwen / Kimi 开放模型跑私有集群；
- Gemini Flash 处理廉价大吞吐；
- GPT / Claude 处理最难任务；
- 同一套 MCP / A2A / internal tools 连接它们。

这意味着“公司应该选开源还是闭源”本身可能就是错误问题。

更实用的问题是：

> **哪一层工作需要哪一种控制权、成本和责任结构？**

Agent 时代的模型选择会越来越像云架构：混合云、多云、私有云并存，而不是全押一个供应商。

---

## 十三、评曰：真正争夺的是控制面

大模型早期的开放争论把权重看得太像传统软件源代码。

权重当然重要。拥有权重意味着原厂无法强制改变你的副本，这是极强的技术自由。

但 2026 年告诉我们，权重并不是全部。

2.8T 权重可以开放，算力仍然集中；闭源模型可以不给权重，却通过标准协议减少工作流锁定；本地 30B 模型能力弱一些，却能把数据和运行权真正留给用户；同一个 Claude 底层模型还可以因为 safeguards 和访问制度不同成为不同风险层。

所以最终争夺的不是一个文件，而是**控制面**：

- 谁决定模型什么时候升级；
- 谁决定它能调用什么；
- 谁保管数据；
- 谁控制算力；
- 谁能撤销访问；
- 谁承担安全事故；
- 谁能把系统迁走。

开源与闭源会继续存在，但边界会越来越像一张拓扑图，而不是一道墙。

真正成熟的判断，不应该问“哪边更正义”，而应该问：

> **对这项智能能力，我们希望把哪些控制权留给供应商，哪些交给用户，哪些交给公共标准，哪些必须由制度约束。**

这才是大模型时代开放问题的长期形态。
