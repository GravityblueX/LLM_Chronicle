# 模型合并与开放权重的未来：从“权重乐高”到运行时组合

> 2023—2024 年，模型合并让社区第一次强烈感受到：一个模型的能力可以在不重新预训练的情况下被重新组合。到 2026 年，这个问题已经扩展得更大。开放生态不只在合并权重，还在做蒸馏、LoRA、量化、架构裁剪、专家路由、模型级 routing，以及把多个 Agent 在运行时并行组合。**“一个模型”没有消失，但能力的生产单位已经从单一权重文件扩展为：基座 + 后训练 + 适配器 + 推理引擎 + Agent runtime。**

---

## 一、模型合并为什么在 2023—2024 年爆发

传统获取新能力的路径是重新训练或微调。

模型合并（model merging）提供了另一条路线：对多个**架构兼容、参数空间可对齐**的模型 / checkpoint 做数学组合，在不重新进行大规模预训练的情况下重组能力。

这里必须纠正一个常见夸张：

> **不是任意两个模型都能直接把权重相加。**

Llama、Qwen、Mistral 等如果架构、shape、tokenizer、参数语义不同，不能像同尺寸同基座微调 checkpoint 那样直接做普通线性平均。

模型合并最容易成立的场景通常是：

- 同一基座的多个 fine-tune；
- 同架构 / 同维度 checkpoint；
- 可以定义参数对应关系的模型；
- 或者使用更复杂的层选择 / 拼接方法。

这是“权重乐高”比喻最需要加上的边界。

---

## 二、TIES、DARE 与 Evolutionary Merge：解决的其实是干扰

简单线性插值很早就存在；大模型合并真正成为社区技术，是因为研究者开始处理不同 fine-tune 之间的**参数冲突**。

**TIES-Merging**通过 trim、符号一致性选择和 merge，试图只保留重要且方向一致的 task vectors。[^1]

**DARE**通过随机丢弃和 rescale delta parameters，降低多模型合并时的干扰。[^2]

**Evolutionary Model Merge**进一步用搜索方法选择层 / 合并配方，而不是人工指定一个固定比例。[^3]

这些方法共同揭示一个事实：

> Fine-tuning 产生的能力变化，并不是完全不可分解的整体；至少其中一部分可以通过参数差值、子空间和层级结构重新组合。

这不意味着我们“理解了知识存在哪里”，但证明参数空间存在可利用的结构。

---

## 三、2024 排行榜为什么充满 merge 模型

mergekit 等工具把模型合并从研究代码变成配置文件和命令行工具。[^4]

社区开始大量合并：

- 一个模型擅长 instruction following；
- 一个擅长 roleplay；
- 一个擅长代码；
- 再通过 TIES / DARE / SLERP / layer merge 等尝试得到折中版本。

它降低了实验门槛，也带来排行榜问题：

某些合并配方可能针对特定 benchmark 形成有利组合，却没有对应的训练故事、数据说明和真实任务验证。

因此“排行榜上更高”并不能自动说明合并产生了稳定的新通用能力。

模型合并最适合被理解成一种**低成本后训练 / 模型组合工具**，而不是无中生有地产生知识。

---

## 四、真正改变 2025—2026 开放生态的，不只有 merge

如果只盯着模型合并，会错过开放权重生态更大的变化。

### 4.1 蒸馏：能力可以跨规模迁移

DeepSeek-R1 同步发布多个基于 Qwen / Llama 的蒸馏模型。[^5]

这比“把两个 checkpoint 平均”更激进：

- 教师模型生成 reasoning / task data；
- 小模型通过后训练吸收行为；
- 能力从一个大权重集合迁移到另一个完全不同尺寸的模型。

开放生态由此拥有“能力复制链”。

### 4.2 LoRA / PEFT：能力作为外挂层存在

低秩适配让基座权重保持不变，领域能力以很小的 adapter 存在。

一个基座可以同时挂多个适配器；能力不再必须和完整模型一一绑定。

### 4.3 量化：同一个模型出现多个运行身份

FP16、FP8、INT8、INT4、GGUF / AWQ / GPTQ 等量化版本让“模型版本”还包含运行形式。

同一组语义能力可能因为量化方式、context、kernel 与硬件不同，表现出完全不同的吞吐和精度。

### 4.4 Router：能力在运行时选择，而不是在权重里永久合并

2025—2026 年，越来越多系统不再试图做一个万能 checkpoint，而是在请求时选择：

- 快模型 / 慢模型；
- reasoning / non-reasoning；
- local / cloud；
- cheap / frontier；
- specialist agent。

GPT-5 的 fast + reasoning + router 统一，就是闭源体系里的明显例子。[^6]

于是“合并能力”的动作从离线权重数学，转向在线调度。

---

## 五、MoE 本身就是一种“模型内部的运行时组合”

MoE（Mixture-of-Experts）提供了另一个视角。

Kimi K3 有 896 routed experts，每 token 选择其中 16 个；Qwen3.8 与 DeepSeek V4 同样使用高度稀疏 MoE。[^7][^8]

这里不存在“先把多个完整模型合并成一个”的社区工作流，但思想上有相似之处：

> **不同参数子系统并不需要每次都一起参与计算。**

router 根据 token / hidden state 动态选择专家。

因此能力组合可以发生在三层：

1. **训练后权重合并**：TIES / DARE / mergekit；
2. **模型内部稀疏路由**：MoE；
3. **系统级模型 / Agent 路由**：不同模型、不同 Agent 在任务级组合。

从 2026 回头看，第三层正在变得最重要。

---

## 六、多 Agent：不再合并权重，直接合并劳动

Kimi Agent Swarm、GPT-5.6 ultra 等系统提供了一个非常直接的新答案：

如果一个模型不需要独自拥有所有能力，那就不要在参数空间强行把能力揉成一个 checkpoint，而是在任务层把工作拆给多个 Agent。[^9][^10]

这是一种**运行时模型合并**：

- researcher Agent 搜资料；
- coder Agent 写实现；
- reviewer Agent 检查；
- visual Agent 看图；
- orchestrator 汇总。

它们的权重甚至可以完全不同。

因此“能力组合”的未来，很可能从 parameter merge 转向**workflow composition**。

模型合并不会消失，但它不再是唯一、甚至未必是最灵活的组合方式。

---

## 七、Kimi K3 / Qwen3.8：权重开放以后，组合门槛反而进入基础设施

2T—3T 级开放权重旗舰带来一个新现实。

过去社区模型合并的浪漫建立在一个前提上：个人 / 小团队至少能把模型加载起来。

**Kimi K3 2.8T**与**Qwen3.8 2.4T**打破了这个前提。[^7][^8]

它们当然可以：

- 研究参数；
- 做专家级裁剪；
- 蒸馏；
- 量化；
- 继续训练；
- 设计新的 serving runtime。

但直接对完整模型做实验需要极大的内存、存储与多机互联。

所以“开放权重民主化”在超大模型时代出现分叉：

- **法律上更开放；**
- **实验基础设施上更昂贵。**

未来开放生态的重要创新，可能不只是 merge algorithm，而是怎样把巨型开放模型**压小、拆分、蒸馏、稀疏化和高效 serving**。

---

## 八、Muse Glimmer：开放生态的另一端是“小到真正属于你”

Meta Muse Glimmer 选择了几乎相反的方向：30B、Apache 2.0、目标是在消费级 GPU 上跑 always-on local agent。[^11]

这提醒我们：

> 开放权重未来不只有“把最强旗舰放出来”，还有“把足够强的模型压到真实用户能拥有”。

在本地 Agent 场景，模型合并 / adapter / quantization 反而可能再次很重要，因为用户会希望把：

- 个人偏好；
- 领域技能；
- 本地工具习惯；
- 私有知识

组合进自己的模型，而不是训练一个新基座。

所以 merge 技术可能从排行榜游戏重新回到“个人模型组装”这个更实际的用途。

---

## 九、许可证问题必须从“哪个父模型”升级为 lineage

旧讨论经常问：

> Llama 许可模型 + Apache 模型 merge 后是什么许可？

这个问题没有简单通用答案，而且直接跨架构权重合并本身常常并不成立。

更现实的 lineage 已经复杂得多：

- 基座 A；
- 使用模型 B 生成的数据蒸馏；
- 加 adapter C；
- merge fine-tune D；
- 量化为 E；
- 再部署进 Agent 系统 F。

此时需要记录的不是“谁是父亲”，而是一张**模型供应链 SBOM**：

- base model；
- weight license；
- training / synthetic data provenance；
- adapter；
- merge recipe；
- quantization；
- inference engine；
- safety layer。

模型 provenance 会越来越像软件供应链管理。

---

## 十、OSAID 的作用：把“模型文件”重新扩展成系统材料

OSAID 1.0 强调使用、研究、修改、分享 AI 系统所需的首选修改形式信息，而不是只问有没有 `.safetensors`。[^12]

这与 2026 的现实越来越契合。

因为当模型行为来自：

- base weights；
- post-training；
- router；
- tool harness；
- runtime policy；

只开放一个权重文件，并不能完整解释系统。

这并不意味着开放权重“不算开放”，而是说明需要更精确地标注开放发生在哪一层。

---

## 十一、模型身份没有瓦解，而是从“文件”变成谱系

旧稿把模型合并描述成“模型身份危机”。这个判断太强。

Linux 有 fork，软件包有依赖，Docker image 有 layer；它们并没有因此失去身份，而是发展出版本、hash、dependency graph 和 provenance。

模型也可能如此。

未来一个模型的身份更可能是：

> **一个可追溯谱系 + 一组权重 + 一个运行配置。**

例如：

- 基于哪个 checkpoint；
- 接受过什么后训练；
- 是否 merge；
- 是否量化；
- context 配置是什么；
- runtime 用哪个 kernel；
- 搭配哪些 tool / system policy。

身份从“一个名字”升级成“一个构建记录”。

这不是瓦解，而是成熟。

---

## 十二、开放权重未来的五条路线

### 路线一：更大开放旗舰

Kimi K3 / Qwen3.8：把前沿权重继续开放。

### 路线二：更小本地 Agent

Muse Glimmer：让模型真正进入个人硬件。

### 路线三：蒸馏 / 压缩

把巨型教师的能力迁移到可部署学生模型。

### 路线四：适配器与组合

LoRA、merge、specialist adapters，让能力成为可安装模块。

### 路线五：运行时编排

用 router / multi-agent / tool protocol 组合能力，而不是把所有能力烧进同一个权重文件。

五条路线会长期并存。

## 评曰：真正可组合的不是模型，而是智能生产链

模型合并最早给人的震撼，是“原来权重也可以像代码一样拼”。

这个直觉是对的，但范围太窄。

到 2026 年，我们已经看到更广泛的组合：

- 参数可以 merge；
- 行为可以 distill；
- 技能可以做成 adapter；
- 专家可以由 MoE router 动态选择；
- 模型可以由 system router 切换；
- Agent 可以在任务层并行协作。

因此真正瓦解的不是“模型身份”，而是另一个旧假设：

> **一个能力必须由一个从头训练、不可拆分的单体模型独占。**

开放权重生态正在把智能变成供应链：基座、后训练、压缩、运行时、工具和 Agent 都可以由不同主体贡献。

这会让许可证、责任与 provenance 更复杂，也会让创新门槛继续下降。

模型合并只是这场变化最早、最直观的预告。

未来真正重要的，不是“还能不能把两个模型平均一下”，而是：

> **我们能否像构建软件系统一样，可靠地组合来自不同来源的智能部件，同时保留可追溯性、许可边界与验证能力。**
