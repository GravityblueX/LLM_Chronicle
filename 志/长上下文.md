# 《长上下文技术志》：从“能塞多少”到“怎样管理长期状态”

> 长上下文最初是一场很直观的数字竞赛：2K、32K、100K、200K、1M。到 2026 年，1M token 已经出现在 Gemini、DeepSeek V4、Kimi K3、Qwen3.8、GLM-5.x 等多条前沿路线里，“谁窗口最大”反而不再是最重要的问题。真正困难的是：**模型是否真的利用得到中间信息、KV / attention 成本如何控制、哪些状态值得长期保留、上下文满了以后如何压缩、以及 Agent 如何在数小时任务中维持连续性。** 长上下文正在从一个模型规格，变成运行时状态管理问题。

---

## 一、上下文窗口究竟是什么

Context window 是一次模型运行中可以直接纳入注意力计算的 token 范围。

它通常同时容纳：

- system / developer instructions；
- 用户输入；
- 对话历史；
- 检索文档；
- 文件和代码；
- 工具定义；
- 工具输出；
- Agent 中间状态。

所以它不是“记忆”本身，更接近**工作内存**。

真正的长期记忆可能存放在数据库、文件、向量索引、用户 profile 或 Agent memory 中；需要时再被加载进 context。

这个区别在 Agent 时代非常重要：把所有历史永远塞进 context，既贵，也不一定更好。

---

## 二、早期：长度直接决定能不能做某类任务

| 时间 | 模型 | 代表窗口 | 史学位置 |
|------|------|----------|----------|
| 2020 | GPT-3 | 2K | 短文本与短对话 |
| 2023-03 | GPT-4 | 8K / 32K | 长文档开始进入通用模型 |
| 2023-07 | Claude 2 | 100K | 数百页材料进入商业 API |
| 2023-11 | Claude 2.1 | 200K | 长上下文成为 Anthropic 差异化 |
| 2024-02 | Gemini 1.5 Pro | 1M（实验更长） | 百万 token 进入主流前沿 |

在这个阶段，窗口每扩展一个数量级，都会直接打开新任务：

- 一篇文章 → 一份合同；
- 一份合同 → 一本书；
- 一本书 → 一个代码库；
- 一个代码库 → 多仓库 / 多文档工作流。

所以“窗口长度”曾经是真正的产品卖点。

---

## 三、位置编码：能不能把模型训练长度之外的位置理解清楚

Transformer 自注意力本身没有顺序概念，需要位置表示。

### 3.1 RoPE

RoPE（Rotary Position Embedding）把位置信息通过旋转作用到 Q/K，使相对位置自然进入 attention score。[^1]

它成为 Llama、Qwen、DeepSeek 等大量开放模型的标准方案。

### 3.2 Position interpolation / YaRN

当模型要从较短训练长度扩展到 32K / 128K 甚至更远，直接外推 RoPE 容易退化。

Position Interpolation、YaRN 等方法通过重新缩放位置频率，让已有模型更稳定地扩展长度。[^2]

但要注意：

> **位置编码能外推，不等于模型真的学会在超长序列里做复杂推理。**

长度支持和长程能力是两件事。

---

## 四、FlashAttention：长上下文的第一个工程地基

标准 attention 在长度 N 上有 O(N²) 的注意力配对计算。

FlashAttention 通过 IO-aware tiling 和在线 softmax 避免将完整 attention matrix 写入 HBM，大幅降低内存流量，并使长序列训练/推理更可行。[^3]

需要纠正旧稿常见的一句话：

> FlashAttention **没有把注意力数学复杂度从 O(N²) 变成 O(N)**。

它主要优化**内存 IO 与实际执行效率**，并把 attention matrix 的显式内存占用降下来；标准 full attention 的计算量仍然随 N² 增长。

这个区别很重要，因为到了百万 token，光靠更聪明的 kernel 仍然不够。

---

## 五、稀疏、线性与混合注意力：百万 token 时代必须少算一些

为了让极长序列经济可行，行业逐渐出现多条路线：

- Sliding Window Attention：只看局部窗口；
- sparse attention：只计算部分连接；
- linear / delta attention：用可压缩状态替代完整 pairwise attention；
- full attention 与高效 attention 混合。

2026 年这种混合已经进入前沿开放模型。

### Kimi K3

Kimi K3 在 93 层中组合 **Kimi Delta Attention（KDA）** 与 Gated MLA，兼顾长上下文效率和 full-attention 类能力。[^4]

### Qwen3.8

Qwen3.8 同样使用混合注意力设计，并支持 1M context。[^5]

### GLM-5.3-Flash

GLM-5.3-Flash 则公开强调 **sparse + linear attention hybrid**，目标是在 1M context 下控制 serving 成本。[^6]

因此“后 Transformer”并不一定表现为完全抛弃 attention，而更可能表现为：

> **只在值得的层和位置使用昂贵的 full attention。**

---

## 六、KV Cache：长上下文真正最常见的运行时税

自回归 decode 需要保存历史 token 的 Key / Value 状态。

上下文越长：

- KV Cache 越大；
- 可同时服务的请求越少；
- batch 越难做大；
- 显存和跨节点通信压力越高。

因此长上下文经济学很大部分其实是**状态存储经济学**。

### MLA

DeepSeek V2 提出的 Multi-head Latent Attention（MLA）通过低维 latent representation 压缩需要保存的 KV 信息。[^7]

旧稿喜欢写“KV Cache 压缩 90%，所以整体推理便宜 90%”，这是不严谨的。

MLA 显著降低的是**KV Cache 这一项**；端到端成本还包括专家计算、attention、通信、采样和工具调用。

但在长 context / 大 batch 场景，KV 正好是最关键瓶颈之一，所以影响仍然巨大。

---

## 七、1M 从“Google 特技”变成前沿常规配置

到 2026 年，多条路线都进入百万 token：

| 模型 | 公开 context | 路线 |
|------|--------------|------|
| Gemini 3.x / Flash | 1M 级 | 云端多模态工作负载 |
| DeepSeek V4 | 1M | Pro / Flash Agent 模型 |
| Kimi K3 | 1M | 2.8T 开放多模态 Agent |
| Qwen3.8 | 1M | 2.4T 开放旗舰 + Flash |
| GLM-5.x | 1M | 长程 coding / Agent / 多模态 |
| Claude Opus 4.6+ | 1M 级能力扩展 | 长任务与 compaction 结合 |

百万 token 因此不再能单独证明“模型更先进”。

下一阶段比较的是：

- 1M 时还能不能准确引用前文；
- attention / KV 成本多少；
- 吞吐还能不能接受；
- 长任务中是否保持 instruction hierarchy；
- 是否会遗忘中间关键信息。

---

## 八、Needle-in-a-Haystack 为什么不够

早期长上下文展示经常使用 Needle-in-a-Haystack：把一句独特事实埋在超长文本中，看模型能否找回。

它有价值，但主要测**检索**。

真实长上下文任务更难：

- 前后几十处证据需要综合；
- 中间信息互相矛盾；
- 需要追踪实体状态；
- 需要在代码库跨文件推理；
- 旧信息后来被新信息覆盖；
- 工具结果不断加入。

这就是著名的 “lost in the middle” 问题：窗口里存在信息，不等于模型会在需要时正确使用。[^8]

所以未来长 context benchmark 应该更多评估**状态追踪和多证据推理**，而不是只找一根针。

---

## 九、Agent 让上下文从“文档长度”变成“任务寿命”

聊天模型的 context 通常被一个问题填满。

Agent 的 context 会在工作中不断增长：

- 第一次计划；
- grep 输出；
- 浏览网页；
- 测试日志；
- 用户修改要求；
- 子 Agent 回报；
- 失败记录。

一个工作数小时的 Agent 很容易积累比初始任务材料更多的**过程信息**。

因此长上下文问题发生变化：

> 不是“能不能一次读一百万 token”，而是“任务进行几个小时以后，哪些东西还应该留在工作记忆里”。

这就是 compaction、memory、checkpoint 出现的原因。

---

## 十、Compaction：上下文满了以后，不是简单截断

Claude Code / Opus 4.x 等长程 Agent 引入越来越系统的 context compaction：

把较早的工作历史压缩成更短的结构化摘要，同时保留：

- 当前目标；
- 已做决策；
- 关键文件；
- 未解决问题；
- 工具状态；
- 必须遵守的约束。

这意味着 Agent 的“记忆”开始出现类似操作系统的层级：

- 热状态：当前 context；
- 压缩状态：summary / checkpoint；
- 冷状态：文件、数据库、logs。

长上下文因此越来越像**memory hierarchy**，而不是无限扩大的一个数组。

---

## 十一、Prompt Caching：长上下文必须能复用

如果一个 500K token 代码库每轮都重新 prefill，长 Agent 会非常昂贵。

Prompt caching 让重复前缀可以复用已计算状态，并配合 cache pricing 降低成本。

在 1M context 时代，cache 不再是“优惠功能”，而是**让超长工作负载具有经济可行性的必要机制**。

这也解释了为什么 API 价格逐渐把：

- uncached input；
- cached input；
- cache write；
- output

拆成不同资源。

“每 1M token 多少钱”已经越来越不能描述真实长上下文成本。

---

## 十二、本地长上下文与云长上下文是两个世界

一个开放模型写着 “1M context” 不等于你的机器真的能跑 1M。

本地部署还受：

- 模型权重显存；
- KV Cache；
- quantization；
- CPU/GPU offload；
- context prefill latency

限制。

因此开放权重模型的 context window 有两个规格：

1. **模型理论 / 官方支持长度**；
2. **你的硬件经济可运行长度**。

Muse Glimmer 这类本地 Agent 的价值，往往不是宣称最大窗口，而是把模型、记忆和工具设计成可以在个人设备持续运行。

---

## 十三、多 Agent 反而可能减少单个 Agent 的 context 压力

多 Agent 系统可以把大任务拆成多个局部 context：

- Agent A 读代码模块；
- Agent B 查外部文档；
- Agent C 做测试；
- orchestrator 只接收压缩结果。

这是一种**context sharding**。

它和分布式系统分片很相似：不是让一个节点保存全部状态，而是让多个执行者维护局部工作集。

但代价是新的协调问题：

- 信息丢失；
- 重复工作；
- 冲突；
- summary distortion。

所以多 Agent 不只是“更多 compute”，也是**状态架构选择**。

---

## 十四、长上下文真正的评价标准

到 2026 年，单列一个 context length 数字已经远远不够。

更合理的表应该至少有：

| 维度 | 评价问题 |
|------|----------|
| Maximum window | 理论能放多少 |
| Effective recall | 中间信息还能找回来吗 |
| Multi-evidence reasoning | 能跨远距离综合吗 |
| Prefill latency | 读进去需要多久 |
| KV / memory cost | 长状态占多少资源 |
| Cache reuse | 重复 context 能否复用 |
| Compaction quality | 压缩后关键决策是否保留 |
| Long-horizon consistency | 数小时后还记得目标吗 |

这才是 Agent 时代真正的长上下文 benchmark。

---

## 评曰

长上下文技术史最初像硬盘容量史：

2K、32K、100K、1M，数字越大越震撼。

但当百万 token 成为多个前沿家族的常规配置，问题突然变了。

真正困难的不再是“能装进去”，而是：

> **装进去以后，怎样以可承受的成本找到、使用、更新、压缩和遗忘。**

人类工作记忆也不是无限保存所有细节。我们会做笔记、写摘要、把资料放进书架，只在需要时取回。

Agent 正在走同一条路。

因此长上下文的终局很可能不是 10M、100M token 的无限窗口，而是一套**分层状态系统**：

**context + cache + memory + retrieval + compaction + checkpoint + subagents。**

窗口长度仍然重要，但它已经从“记忆能力”降级成其中一层。

从“读得更多”到“管理更久”，这才是 2026 年长上下文真正的转折。
