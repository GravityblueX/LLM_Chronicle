# 《长上下文技术志》

> 大模型的上下文窗口，决定了它一次能"看"多少东西。从 GPT-3 的 2048 个 token 到 Gemini 1.5 Pro 的 100 万个 token，四年内上下文长度扩展了近 500 倍——这不是一个量变，而是一个质变。它改变了"什么任务可以交给大模型"的边界：从回答一段话，到阅读整本书、分析整个代码库、理解数百页法律合同。这条演化路上，RoPE、YaRN、Ring Attention、MLA 等技术接力解决了一个又一个工程和算法瓶颈。这里记录的，是大模型如何学会"一次读更多"的技术史。

---

## 一、概述

上下文窗口（Context Window）是大语言模型在单次推理中能处理的 token 数量。它既是模型的记忆容量，也是模型与用户之间的信息通道——所有用户输入、系统指令、历史对话、参考文档，都要塞进这个窗口里。

上下文窗口的大小，直接决定了模型能完成的任务类型：

- **2K tokens**（GPT-3，2020）：只能处理几段文字，适合短对话和简单问答。
- **8K—32K tokens**（GPT-4，2023）：能处理一份中等长度的文档，适合文档分析和代码理解。
- **100K—200K tokens**（Claude 2/2.1，2023）：能处理数百页文档，适合长文阅读和法律分析。
- **1M—2M tokens**（Gemini 1.5 Pro，2024）：能处理整本书或整个代码库，适合大规模知识检索和多文档推理。

上下文长度的扩展不是简单的"放大数字"——它涉及一系列连锁的技术挑战：位置编码的外推能力、注意力计算的平方复杂度、KV Cache 的显存占用、以及长文本中信息"遗失在中间"的问题。

## 二、位置编码的演化：从正弦到旋转

Transformer 的核心计算——自注意力——本身不包含位置信息。Q、K、V 都是从 token 的语义表示中线性投影出来的，如果不额外注入位置信号，模型无法区分"第 1 个词"和"第 100 个词"。位置编码（Positional Encoding）就是为了解决这个问题。

### 2.1 正弦位置编码：Transformer 的原方案

2017 年 Transformer 论文使用的是**正弦位置编码**（Sinusoidal Positional Encoding）：用一组不同频率的正弦和余弦函数生成位置向量，加到 token 的嵌入上。[^1] 这个方案简单、无需训练参数，但有一个关键弱点：**外推能力差**。模型在训练时只见过一定长度的位置，推理时如果序列超出训练长度，位置编码的值域超出模型见过的范围，性能急剧下降。

### 2.2 RoPE：旋转位置编码

2021 年，苏剑林（Su Jianlin）提出 **RoPE（Rotary Position Embedding，旋转位置编码）**。[^2] RoPE 的核心思想是：不把位置编码"加"到嵌入上，而是用旋转矩阵"乘"到 Q 和 K 上——让每一对 Q 和 K 之间的内积自然地依赖于它们的相对位置。

RoPE 的优势在于：

1. **相对位置敏感**：注意力分数只取决于两个 token 之间的距离，而非绝对位置。
2. **与线性注意力兼容**：旋转操作保持了向量的范数，不改变注意力的计算结构。
3. **良好的外推性**：理论上，RoPE 对训练时未见过的相对位置仍然有合理的泛化能力。

RoPE 迅速成为开源模型的标准位置编码方案——LLaMA、Mistral、Qwen、DeepSeek 系列全部采用 RoPE。它为后续的长上下文扩展提供了基础。

但 RoPE 的外推能力并非无限。当推理长度远超训练长度时（例如训练 4K、推理 128K），RoPE 的旋转角度会超出训练分布，导致注意力分数异常——模型开始"糊涂"。

### 2.3 YaRN：让 RoPE 泛化到更长的序列

**2023 年**，Peng et al. 提出 **YaRN（Yet another RoPE extensioN）**，解决了 RoPE 在长序列上的外推问题。[^3]

YaRN 的核心观察是：RoPE 的旋转频率可以分为高频分量和低频分量——高频分量编码局部位置关系（相邻 token 之间的距离），低频分量编码全局位置关系（远距离 token 之间的距离）。高频分量不需要修改，但低频分量在超出训练长度时会"溢出"——YaRN 通过频率缩放（对低频分量的旋转角进行插值）来修正这个问题。

YaRN 的效果是：**一个在 4K 长度上训练的模型，通过 YaRN 可以在 128K 甚至更长的上下文中保持良好性能**——只需少量的微调（几百步）就能完成长度外推。这使得"短上下文训练 + 长上下文推理"成为可行的技术路线，大幅降低了长上下文模型的训练成本。

## 三、注意力计算的效率瓶颈

位置编码解决了"模型能不能理解长序列"的问题，但另一个瓶颈更为实际：**注意力计算的复杂度是 O(N²)**。

标准自注意力需要计算所有 token 两两之间的注意力分数——一个长度为 N 的序列，需要计算 N×N 的注意力矩阵。当 N=4096 时，这个矩阵有 1600 万个元素；当 N=128K 时，超过 160 亿个元素。这不仅是计算量的问题，更是内存的问题——注意力矩阵需要完整地存在于 GPU 显存中。

### 3.1 FlashAttention：算法层面的内存革命

**FlashAttention**（Tri Dao et al., 2022）通过分块计算（tiling）和在线 softmax 算法，避免了将完整的注意力矩阵写入 GPU 的 HBM（高带宽显存），将注意力的内存占用从 O(N²) 降至 O(N)。[^4] FlashAttention-2（2023 年 7 月）进一步优化了并行度，性能再提升约 2 倍。[^5]

FlashAttention 的意义不仅是"更快"——它使长上下文推理在工程上成为可能。没有 FlashAttention，128K 上下文的推理需要的显存超出单台 GPU 的能力；有了 FlashAttention，长上下文推理可以在消费级 GPU 上实现。

（FlashAttention 的完整技术故事，详见《FlashAttention 列传》。其在推理优化中的角色，详见《推理优化志》。）

### 3.2 Ring Attention：分布式长上下文

当上下文长度进一步扩展到 1M tokens 时，即使有 FlashAttention，单台 GPU 的显存仍然不够。**Ring Attention**（2023，Liu et al.）提出了一种分布式注意力计算方案：将长序列切分为多个块，分配到多台 GPU 上，每台 GPU 计算自己负责的 Q 与其他 GPU 上的 KV 之间的注意力——通过环形通信（ring communication）在 GPU 之间传递 KV 块。[^6]

Ring Attention 的关键性质是：**通信和计算可以重叠**——当一台 GPU 在接收下一块 KV 时，它可以同时计算当前块的注意力。这使得 Ring Attention 的效率接近理论上限：在 P 台 GPU 上处理长度为 N 的序列，每台 GPU 的显存需求降为 N/P，而总计算时间几乎不增加。

Ring Attention 是 Google Gemini 1.5 Pro 实现 1M token 上下文的关键技术之一。[^7]

### 3.3 滑动窗口注意力

**滑动窗口注意力（Sliding Window Attention, SWA）** 是另一种降低注意力复杂度的方案：每个 token 只关注其附近固定窗口大小（例如 4096 个 token）内的其他 token，而非全部历史。[^8]

SWA 的优势是简单且高效——复杂度从 O(N²) 降为 O(N×W)（W 为窗口大小），且不需要额外的训练技巧。Mistral 7B（2023-09）是第一个采用 SWA 的主流开源模型。[^8]

但 SWA 的局限也很明显：它本质上牺牲了"远距离信息"来换取效率。超出窗口范围的历史 token 完全不被注意——对于需要全局理解的任务（例如"总结这份 100 页报告的前三页和最后三页有什么关联"），SWA 可能遗漏关键信息。

### 3.4 MLA：DeepSeek 的 KV Cache 革命

**Multi-head Latent Attention（MLA）** 由 DeepSeek 在 V2 模型（2024-05）中提出，是长上下文推理优化领域最具原创性的架构创新。[^9]

MLA 的核心思路与前面的方法不同——它不修改注意力的计算范围，而是压缩 KV Cache。标准注意力需要为每个 token 缓存完整的 Key 和 Value 向量；MLA 将 KV 投影到一个低维潜在空间，只缓存低维表示，计算时再重建。这使得 KV Cache 压缩到原来的 5%-10%，大幅降低了长上下文推理的显存需求。[^9]

（MLA 的完整技术分析，详见《推理优化志》§2.2。）

## 四、上下文长度的军备竞赛（2023—2025）

技术突破推动了上下文窗口的军备竞赛。以下是关键里程碑：

| 时间 | 模型/产品 | 上下文窗口 | 关键意义 |
|------|----------|-----------|---------|
| 2020-06 | GPT-3 | 2,048 tokens | 奠基者 |
| 2023-03 | GPT-4 | 8K / 32K tokens | 首次提供两种上下文选项 |
| 2023-07 | Claude 2 | 100K tokens | 首个商用 100K 模型[^10] |
| 2023-11 | GPT-4 Turbo | 128K tokens | OpenAI 追平长上下文竞争 |
| 2023-11 | Claude 2.1 | 200K tokens | Anthropic 再次领先[^11] |
| 2024-02 | Gemini 1.5 Pro | 1M tokens（测试态 10M） | 长上下文进入百万时代[^7] |
| 2024-03 | Claude 3 | 200K tokens | 标准上下文维持 200K |
| 2024-10 | Claude 3.5 Sonnet (v2) | 200K tokens | 长上下文 + 编程能力结合 |
| 2025-01 | DeepSeek-R1 | 128K tokens | 推理模型同样关注长上下文 |

**Gemini 1.5 Pro**（2024-02）是这轮竞赛的高光时刻。[^7] 它将上下文窗口推到 1M tokens——约 70 万词或几本长篇小说的体量。Google 在技术报告中展示了在 10M token 上下文下的"大海捞针"（Needle-in-a-Haystack）测试结果：即使在 1000 万 token 的上下文中，模型仍然能准确找到隐藏在中间的特定信息。

Google 的技术突破建立在 MoE（Mixture-of-Experts）架构和 Ring Attention 的基础上。1M token 的上下文对单次推理的计算量巨大，但 MoE 的稀疏激活机制——每个 token 只激活部分专家——有效控制了计算成本。

## 五、Kimi：中国市场的长上下文差异化

在中文互联网市场，长上下文成为了一个出乎意料的产品差异化卖点。

**2024 年 3 月**，Moonshot AI 发布 **Kimi 智能助手**，主打"200 万字超长上下文"——约 200 万汉字，相当于 2M tokens。[^12] Kimi 的产品定位是"让 AI 一次性阅读整本书"——用户可以上传一本完整的小说、一份完整的财报、甚至一个完整的代码库，Kimi 一次性理解全部内容。

Kimi 在中国市场的成功反映了一个有趣的市场逻辑：**长上下文在技术上是"锦上添花"，但在产品上是"杀手特性"。** 对普通用户来说，"AI 能读完整本书"比"AI 在 MMLU 上高 2 个百分点"更有感知。Kimi 把一个技术参数变成了产品卖点——这是长上下文军备竞赛中最具商业化智慧的操作之一。

Kimi 的技术基础部分来自 Moonshot AI 对长上下文训练和推理的工程优化，包括分块注意力、KV Cache 压缩、以及对 RoPE 的外推扩展。[^12] 但 Kimi 更重要的贡献是**市场教育**：它让中文互联网用户第一次直观感受到"长上下文"意味着什么。

## 六、长上下文 vs RAG：替代还是互补？

长上下文窗口的扩大引发了一个持续的争论：**如果模型能一次读完所有文档，还需要 RAG（检索增强生成）吗？**

RAG 的核心逻辑是：模型的知识是静态的（参数里），需要实时检索外部知识来补充。当上下文窗口只有 4K tokens 时，把一份 100 页的文档切成碎片、用向量检索找到最相关的段落、拼进上下文——这是唯一可行的方案。但当上下文窗口达到 1M tokens，把整份文档直接塞进上下文就成为可能——不需要切片，不需要检索，不需要担心跨段落推理的丢失。

Anthropic 在 Claude 2 的发布博客中明确提出了这个对比："对于复杂问题，[长上下文]很可能比基于向量搜索的方法好得多。"[^10]

但现实中，长上下文并不能完全替代 RAG。原因有三：

1. **成本**：1M token 的上下文意味着每次推理的费用可能达到数美元——对于高频调用的客服、搜索、知识库场景，这个成本不可接受。RAG 检索到的最相关段落通常只有几千 token，成本低两个数量级。
2. **知识新鲜度**：长上下文加载的是用户提供的文档，RAG 可以实时检索最新信息。一份每天更新的数据库，不适合每次查询都把整个数据库塞进上下文。
3. **信息定位**：虽然 Gemini 1.5 Pro 在"大海捞针"测试中表现优异，但在 1M token 的上下文中，模型对中间部分信息的关注度仍然低于首尾——这被称为"Lost in the Middle"问题。[^13] RAG 的检索步骤天然避免了这个问题。

因此，更准确的判断是：**长上下文和 RAG 是互补的，而非替代的。** 长上下文适合"一次性处理大量文档"的场景（法律分析、代码理解、书籍问答），RAG 适合"高频、低成本、实时更新"的场景（客服、搜索、知识库）。在实践中，最强大的系统往往是两者结合：用 RAG 从海量知识库中检索相关文档，再用长上下文窗口将检索结果和用户问题一起交给模型处理。

（RAG 的完整技术故事，详见《RAG 列传》。）

## 七、上下文长度的技术天花板

尽管上下文窗口已经扩展到 1M tokens，但仍存在几个尚未完全解决的技术挑战：

**Lost in the Middle**：2023 年 Stanford 和 UC Berkeley 的研究发现，即使上下文窗口足够大，模型对上下文中间部分的信息检索和推理能力显著弱于首尾。[^13] 这意味着"能装下"不等于"能用好"——模型处理 1M token 的上下文时，并非所有 token 被同等对待。

**推理成本**：上下文越长，推理的计算量和内存消耗越大。虽然 FlashAttention 和 MLA 等技术显著缓解了这个问题，但 1M token 上下文的单次推理成本仍然远高于 4K token。对于需要实时响应的场景，长上下文的延迟也是实际问题。

**训练数据的稀缺**：训练一个真正能"理解"1M token 上下文的模型，需要大量超长文本的训练数据——但互联网上的文本大多数远短于此。虽然技术文档、法律合同、书籍等长文本源存在，但质量参差不齐，且涉及版权和隐私问题。

**评测方法的不足**：当前的长上下文评测（如"大海捞针"）主要测试信息检索能力——能否在长文本中找到特定信息。但对于长上下文更重要的能力——跨段落推理、全局理解、多文档关联——缺乏成熟的评测基准。

## 评曰

长上下文的技术演化，揭示了大模型发展中一个反复出现的模式：**先突破限制，再优化效率。**

GPT-3 只有 2K 的上下文窗口——不是因为研究者不想要更长的上下文，而是因为注意力的 O(N²) 复杂度在当时是一个硬性限制。RoPE 给了位置编码外推的可能性，FlashAttention 把注意力的内存瓶颈打碎了，YaRN 让短训练长度泛化到长推理长度，Ring Attention 用分布式方案突破了单 GPU 的显存极限——每一步技术突破都在扩展上下文长度的可行边界。

但"能装下更多"不等于"能理解更多"。Lost in the Middle 问题提醒我们：上下文长度是一个"容量"指标，不是"能力"指标。一个能装 1M token 的模型，如果对中间 90% 的内容视而不见，它和一个只装 100K token 的模型在实际能力上没有区别。

长上下文的终极价值不在于"更长"，而在于"更全"——让模型能在一次推理中建立跨越数万 token 的因果链、对比多个文档的矛盾之处、综合数百页信息做出判断。当前的模型已经"能装下"很多，但距离"真正理解"所装下的内容，还有不小的距离。
