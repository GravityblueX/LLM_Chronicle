# 《推理优化志》：从单卡 kernel 到分布式 Agent Serving

> 推理优化曾经主要是“怎样让一个模型更快吐 token”。到 2026 年，生产负载已经变成 1M context、MoE、视觉输入、reasoning、工具调用和长程 Agent；模型可以跨几十张甚至更多加速器，用户还希望低延迟、低价、可缓存、可峰谷调度。于是推理优化从 FlashAttention / INT4 这样的单点技巧，演化成一套完整 serving system：**attention、KV、quantization、speculation、batching、prefill/decode separation、expert parallelism、cache、scheduler 与硬件适配共同决定一项任务能否经济地运行。**

---

## 一、先纠正一个常见误解：推理成本不是“参数量 × token”这么简单

真实 LLM serving 至少包含：

- 读取模型权重；
- prefill 输入上下文；
- attention / KV state；
- decode 输出 token；
- MoE expert routing；
- 跨卡通信；
- sampling；
- tool / Agent runtime。

因此两个 active parameters 相近的模型，也可能因为 context、attention、通信和 runtime 不同而有完全不同的成本。

推理优化的目标也不只有 tokens/s。

还包括：

- time-to-first-token；
- inter-token latency；
- throughput；
- memory per request；
- cost per successful task；
- concurrency；
- tail latency。

---

## 二、FlashAttention：优化 IO，不是把 full attention 变成线性复杂度

FlashAttention 通过 tiling 和 online softmax 减少 Q/K/V 与 attention 中间结果在 HBM 和片上 SRAM 之间的 IO。[^1]

它的重要意义是：

- 更高实际吞吐；
- 更低 attention memory footprint；
- 更长序列可行。

但需要纠正旧稿常见说法：

> **FlashAttention 没有把标准 full attention 的计算复杂度从 O(N²) 改成 O(N)。**

它优化的是执行和内存 IO。

当 context 进入百万 token，系统仍需要 sparse / linear / hybrid attention 等进一步减少实际计算。

---

## 三、KV Cache：decode 时代最昂贵的状态之一

自回归生成每一步都需要历史 token 的 Key / Value。

context 越长，KV Cache 越大，也越限制 batch size 和并发。

### MQA / GQA

Multi-Query Attention 与 Grouped-Query Attention 让多个 query heads 共享较少 KV heads，减少 cache。

### MLA

DeepSeek V2 提出的 Multi-head Latent Attention（MLA）更进一步，将 KV 压缩为低维 latent representation。[^2]

它显著降低 KV Cache，但不能简单写成“整个推理成本降低 90%”。

降低的是一个关键组成项；真实端到端收益取决于负载。

在长上下文、高 batch 和 Agent 场景，这个组成项恰好非常重要。

---

## 四、2026 的注意力路线：full attention 只在值得时使用

百万 context 让“每层都做完整 attention”越来越昂贵。

前沿开放模型开始公开采用混合结构：

- **Kimi K3**：Kimi Delta Attention + Gated MLA；[^3]
- **Qwen3.8**：hybrid attention；[^4]
- **GLM-5.3-Flash**：sparse + linear attention hybrid；[^5]
- DeepSeek V4：继续在 MLA / sparse serving 路线上扩展。

这代表一个重要变化：

> attention 不再是一个统一算子，而是一套按层、按距离、按任务分配精确计算的预算。

“后 Transformer”更可能是混合化，而不是某天突然完全替换 Transformer。

---

## 五、MoE：FLOPs 降下来，通信问题冒出来

MoE 用稀疏激活扩大总容量。

例如：

- DeepSeek V4-Pro：1.6T / 49B active；
- Kimi K3：2.8T / 104B active；
- Qwen3.8：2.4T / 95B active。

理论上每 token 不需要跑全部参数。

但 MoE 引入新的 serving 税：

- expert routing；
- all-to-all communication；
- load imbalance；
- expert placement；
- hot experts；
- 跨节点 bandwidth。

因此 MoE 推理优化越来越像分布式系统问题。

仅看 active parameters 会低估通信成本。

---

## 六、Expert Parallelism：2T 模型不是“放进显存”就结束

巨型 MoE 的专家需要分布在多卡、多机。

serving runtime 必须决定：

- 哪个 expert 放哪张卡；
- routing 结果怎样传输；
- 怎样避免某些卡过载；
- prefill 与 decode 是否使用同一资源布局。

这使网络互联、RDMA、NVLink / 其他互联和拓扑感知调度成为模型性能的一部分。

开放 2.8T 权重并不意味着部署民主化，因为高效 expert parallel serving 本身就是稀缺能力。

---

## 七、Quantization：从“把 7B 放进显卡”到前沿 serving 标配

量化最早在开源社区主要用于本地运行：INT8、INT4、GPTQ、AWQ。

现在它也进入大型云端 serving。

常见方向包括：

- weight-only INT8 / INT4；
- FP8 weight / activation；
- MXFP4 / MXFP8；
- mixed precision experts；
- KV quantization。

DeepSeek V3 的 FP8 训练和 Kimi K3 的低精度设计，都说明低精度已经从“部署后压缩”进入模型设计阶段。[^6]

重要的是：

> **量化收益与硬件支持高度相关。**

一个格式理论上更小，不代表目标芯片有高效 kernel。

所以模型开放之后，runtime / kernel 生态决定量化是否真能转化成成本优势。

---

## 八、Speculative Decoding：串行 decode 的核心加速路线

自回归 decode 天生逐 token 串行。

Speculative Decoding 使用便宜的 draft process 预测多个候选 token，再由目标模型批量验证；如果候选接受率足够高，可以显著提高 decode 吞吐而保持目标分布。[^7]

后续出现：

- Medusa；
- EAGLE；
- self-speculation；
- Multi-Token Prediction-based speculation。

DeepSeek V3 的 MTP 也可以服务 speculative decoding。

因此训练目标与推理优化开始共同设计，而不是训练完再由 serving 团队“补救”。

---

## 九、PagedAttention 与 Continuous Batching：推理框架成为基础设施

vLLM 的 PagedAttention 将 KV Cache 管理借鉴操作系统分页思想，减少预留浪费和碎片；continuous batching 则动态把新请求塞进正在运行的 batch。[^8]

这两项让 LLM serving 从“一个请求一个 batch”转向高利用率在线系统。

今天 vLLM、SGLang、TensorRT-LLM 等 runtime 的竞争，已经和模型本身同样重要。

一个 checkpoint 是否“好用”，很大程度取决于这些框架多久支持：

- 新 attention；
- 新 quantization；
- 新 MoE layout；
- 新 multimodal encoder。

开放模型生态的真正速度，往往由 runtime merge PR 的速度决定。

---

## 十、Prefill / Decode Separation：长上下文与长输出需要不同机器

Prefill 和 Decode 的计算特征不同：

- prefill 计算密集、容易并行；
- decode 更受 memory bandwidth 和 latency 影响。

因此新一代 serving 开始进行 P/D disaggregation：让不同 GPU 甚至不同节点分别承担 prefill 与 decode。

**GLM-5.3-Flash** 官方技术文章描述更进一步的 **Encode–Prefill–Decode（EPD）** 解耦 serving，并在国产 AI 加速器上承担 Ox-Alpha 匿名测试流量。[^5]

这件事非常值得入史：

> 模型架构已经开始围绕 serving pipeline 的物理阶段被拆分部署。

“一个模型运行在一个 GPU 集群”越来越像过度简化。

---

## 十一、Prompt Cache：不重复做相同 prefill

长 Agent 会反复携带：

- system prompt；
- tool schema；
- repo context；
- 文档前缀；
- 会话历史。

如果每轮完整 prefill，成本巨大。

Prompt caching 让重复前缀复用计算状态。

这也是为什么 API 逐渐出现：

- cache write；
- cached input；
- cache hit / miss

不同价格。

在 1M context 时代，cache 是 serving primitive，而不是优惠功能。

---

## 十二、Agent Serving：吞吐单位从 request 变成 session

传统 API 请求几十秒结束。

Agent session 可以持续：

- 几十分钟；
- 几小时；
- 反复调用工具；
- 创建 subagents；
- 保留 checkpoint。

这使 scheduler 面临完全不同的问题：

- 长短任务公平性；
- session affinity；
- cache 生命周期；
- retry budget；
- tool wait time；
- idle resource reclaim。

因此“最大 tokens/s”未必代表最好的 Agent serving。

可能更重要的是：

> **每张卡每天能完成多少真实任务。**

---

## 十三、Peak / Off-Peak Pricing：调度开始直接暴露给用户

DeepSeek V4-Pro / Flash 引入峰谷价格，说明推理集群利用率已经直接进入 API 产品设计。

Batch API、priority tier、Fast mode 等也是同一个逻辑：

- 延迟不敏感任务排到低价时段；
- 高优先级任务多付费；
- 异步 workload 用更高 batch 提高利用率。

于是 serving scheduler 不再只是后台内部实现，而成为**公开经济接口**。

---

## 十四、国产硬件适配：推理优化成为供应链能力

中国模型在 2025—2026 年越来越重视：

- Huawei Ascend；
- Cambricon；
- Moore Threads；
- 其他国产加速器；
- SGLang / vLLM 定制 backend。

GLM-5.3-Flash 官方称匿名测试真实流量全部由国产 AI 芯片提供，说明“支持国产卡”已经从 demo 进入 production serving。[^5]

真正的硬件自主不是模型“能跑起来”，而是：

- 低延迟；
- 高并发；
- 稳定；
- runtime feature 完整；
- 经济可行。

这也是推理优化的地缘政治维度。

---

## 十五、Local Inference：另一种优化目标是控制权

Ollama、llama.cpp、GGUF、MLX 等生态追求的不只是最低云成本。

本地推理优化的目标可能是：

- 数据不出设备；
- 离线可用；
- 固定硬件无边际 API 费；
- 用户拥有模型和 memory。

Muse Glimmer 这类 30B always-on local agent 证明，“更小、更好部署”本身正在重新成为前沿产品目标。

云端优化追求集群利用率；本地优化追求**自主性与有限硬件可用性**。

二者是不同经济学。

---

## 十六、推理优化真正的公式

到 2026 年，推理成本更接近：

**Cost(task) = prefill + decode + KV state + expert communication + tool runtime + retries + parallel agents - cache reuse。**

任何只优化其中一项的技术，最终都要放进整个系统测。

所以“某技术快 2×”不能直接推出“API 成本减半”。

真正应该测的是端到端 workload。

---

## 评曰

推理优化史最初是 GPU kernel 史。

FlashAttention 更快，PagedAttention 更省显存，INT4 让模型塞进小卡。

到 2026 年，这已经变成**分布式智能基础设施史**。

一个 2.8T MoE Agent 要经济运行，需要同时解决：

- attention；
- expert routing；
- KV；
- quantization；
- cache；
- prefill/decode；
- scheduler；
- tool wait；
- subagent parallelism；
- hardware backend。

任何一个环节效率差，都可能吞掉其他算法优化带来的收益。

所以真正的“模型效率”已经不能只归功于模型论文。

它是：

> **architecture × kernels × runtime × hardware × scheduler。**

这也解释了为什么开放权重以后，最稀缺的东西仍然可能是高效运行权重的工程能力。

权重可以一天下载完。

serving stack 往往需要几年积累。
